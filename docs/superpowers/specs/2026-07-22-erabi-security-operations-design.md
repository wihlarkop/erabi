# Erabi Security, Reliability, and Operations Design

**Status:** Approved specification
**Date:** 2026-07-22

## 1. Security Posture

The MVP is single-user and local-first, but it handles untrusted webpages, downloaded files, database credentials, backups, and optional network exposure. Security controls are therefore required even without a full account system.

Principles:

- localhost-only by default;
- explicit exposure and authentication;
- secrets only from environment variables;
- same-origin UI and API;
- untrusted content isolated;
- conservative request parsing;
- structured redacted logs;
- Recovery Mode instead of unsafe partial operation.

## 2. Environment Configuration

`.env` and operating-system environment variables contain secrets and bootstrap connection configuration only.

Examples:

```text
ERABI_HOST=127.0.0.1
ERABI_PORT=7878
ERABI_ACCESS_TOKEN=...
CRAWL4AI_BASE_URL=http://crawl4ai:11235
CRAWL4AI_API_TOKEN=...
TURSO_DATABASE_URL=...
TURSO_AUTH_TOKEN=...
TURSO_EXPORT_TOKEN_SCANDAL=...
ERABI_CORS_ALLOWED_ORIGINS=...
ERABI_OPENAPI_ENABLED=false
```

Priority:

```text
OS environment
→ .env
→ built-in non-secret default
```

`.env` is ignored by Git. `.env.example` contains names and documentation but no secrets.

Non-secret runtime settings such as concurrency, rate limits, retention, screenshot defaults, User-Agent, UI preferences, and backup schedules live in the application database.

## 3. Network Binding

Default:

```text
ERABI_HOST=127.0.0.1
ERABI_PORT=7878
```

This requires no login.

Any non-loopback bind, including `0.0.0.0`, requires `ERABI_ACCESS_TOKEN`. Erabi refuses startup without a token.

Remote deployments should use a reverse proxy with HTTPS. The diagnostic page displays current bind, exposure, token configuration state, and CORS state.

## 4. Shared Access Token

The MVP uses one Bearer token only for non-loopback access.

Protected surfaces include:

- all mutation APIs;
- SSE streams;
- asset and artifact downloads;
- exports;
- backups;
- detailed diagnostics;
- OpenAPI when enabled remotely.

The UI stores the token:

- in `sessionStorage` by default;
- in `localStorage` only after `Remember on this device` is explicitly selected.

A `Forget token` action is always available.

The token never appears in URLs, logs, event payloads, Turso, diagnostics, export manifests, or backup metadata.

Failed authentication attempts are rate-limited and written to a redacted security log.

## 5. Same-Origin and CORS

The SvelteKit UI and Axum API share one origin by default. CORS is disabled.

External frontend origins require an explicit allowlist. Wildcard origin is prohibited when access-token authentication is active.

Preflight permits only required methods and headers. Browser credentials are not enabled by default. SSE uses the same origin and token rules.

Invalid insecure CORS combinations either prevent startup or produce a blocking configuration error.

## 6. Request Hardening

State-changing requests must:

- pass trusted Host validation;
- pass Origin validation for browser requests;
- use the expected Content-Type;
- respect endpoint-specific body-size limits;
- use typed deserialization;
- reject malformed or ambiguous requests;
- reject unknown fields on sensitive operations where ignoring them could be dangerous;
- receive a trace ID for any rejection.

JSON endpoints accept `application/json`. Upload endpoints explicitly accept `multipart/form-data`. Generic form posts and `text/plain` mutation payloads are rejected.

Database access uses parameterized statements.

Restore, permanent deletion, Empty Trash, and network/security changes require dedicated confirmation UI.

## 7. Security Headers

Production responses use a strict policy including:

- Content-Security-Policy;
- `X-Content-Type-Options: nosniff`;
- `Referrer-Policy: no-referrer`;
- restrictive Permissions-Policy;
- Cross-Origin-Opener-Policy;
- Cross-Origin-Resource-Policy;
- frame restrictions.

The production UI avoids `unsafe-eval`, broad wildcard sources, and arbitrary inline scripts.

Development may use a documented relaxed policy only where required by tooling.

## 8. Untrusted Preview Isolation

Crawled HTML is hostile input.

The main UI never injects raw HTML. Sanitized previews run in a sandboxed isolated document with:

- scripts disabled;
- forms disabled;
- navigation disabled;
- no same-origin access;
- external embeds disabled;
- controlled resource loading;
- internal selection identifiers generated by Erabi.

Sanitizer behavior has security fixtures and regression tests.

## 9. Downloaded File Safety

Downloaded assets are untrusted.

Required controls:

- never open or execute automatically;
- sanitize filename and path;
- reject `..`, absolute paths, drive prefixes, reserved Windows device names, control characters, and misleading separators;
- do not follow symlinks;
- store within an isolated asset root;
- assign a unique identifier on collision;
- verify MIME using content where practical rather than trusting extension;
- record size and checksum;
- use streaming writes and atomic finalization;
- clean partial files after cancel/failure;
- enforce per-file and per-run limits;
- deliver through `Content-Disposition: attachment`;
- do not auto-extract archives;
- warn on executable files and MIME/extension mismatch.

Only safe image formats receive controlled preview endpoints. Other files display metadata and an explicit download action.

## 10. OpenAPI

On localhost, OpenAPI JSON and interactive documentation are enabled by default.

On non-loopback exposure, OpenAPI is disabled unless `ERABI_OPENAPI_ENABLED=true`. When enabled remotely, it requires the access token.

Internal-only or sensitive endpoints may be excluded. Examples never contain real user data, URLs, or credentials.

## 11. Structured Tracing

Erabi uses the Rust `tracing` ecosystem.

### Formats

- local development: human-readable, compact, aligned;
- Docker/production: JSON, one event per line.

### Required context

When available:

- timestamp;
- level;
- target/module;
- stable event name;
- message;
- trace ID;
- job ID;
- Crawl Run ID;
- Source ID;
- attempt;
- duration;
- stable error code;
- recoverable flag.

### Event naming

```text
system.starting
system.ready
system.recovery_mode_entered
database.migration.started
database.migration.completed
database.integrity.failed
job.queued
job.started
job.checkpointed
job.failed
crawl.page.loading
crawl.page.completed
crawl.schema_drift_detected
extraction.completed
validation.failed
record.approved
export.completed
backup.completed
storage.critical
```

One primary event represents one occurrence. Stack traces and multiline details remain expandable in the UI.

### Levels

- DEBUG: internal diagnostic detail;
- INFO: normal lifecycle;
- WARN: degraded but continuing;
- ERROR: failed operation or required action.

## 12. Log Redaction

Default logs redact:

- authorization, cookies, and sensitive headers;
- tokens, passwords, and connection strings;
- query parameters;
- request and response bodies;
- extracted values;
- full sensitive URLs when not required.

URLs are reduced to safe origin/path representations where possible.

Diagnostic detail mode:

- explicit opt-in;
- visible warning;
- automatic expiry;
- audit event on enable and disable;
- still never reveals secrets;
- diagnostic bundle performs a second redaction pass.

Detailed logs follow retention. Stable error summary, code, trace ID, and audit evidence persist.

## 13. System Diagnostics

UI and `erabi doctor` inspect:

- database connection and schema version;
- lightweight integrity state;
- artifact directory permissions;
- disk space and thresholds;
- Crawl4AI connectivity and reported version;
- network bind and access-token state;
- CORS and OpenAPI exposure;
- queue and stale jobs;
- process lock;
- backup directory;
- Erabi, Rust, Turso SDK, and build versions.

A diagnostic bundle excludes user URLs, record values, raw artifacts, and assets by default. Secrets are always redacted.

## 14. Startup Sequence

```text
1. Resolve and validate data directory
2. Acquire exclusive process lock
3. Open application database
4. Acquire migration lock
5. Run pending migrations
6. Run lightweight integrity check
7. Verify artifact directories and disk state
8. Recover stale jobs
9. Rebuild in-memory concurrency state
10. Health-check Crawl4AI
11. Start Axum API and workers
12. Report READY or DEGRADED
```

Crawl4AI failure yields `DEGRADED`, not application shutdown.

## 15. Single-Instance Lock

Only one active `erabi serve` may use a local data directory.

Lock metadata includes:

- PID;
- startup time;
- Erabi version;
- bind address;
- data-directory identity.

A second instance exits with a clear message and the running address. A stale lock is reclaimed only after verifying that its owning process is no longer active.

Multi-instance operation is deferred to remote Turso and distributed-worker architecture.

## 16. Migrations and Recovery Mode

`erabi serve` runs migrations automatically under a migration lock.

If migration or integrity verification fails, Erabi enters Recovery Mode:

- UI and diagnostics remain available;
- database is read-only to the extent safely possible;
- workers, scraping, approval, exports, retention, and mutations are disabled;
- error and trace ID are shown;
- backup verification and restore remain available;
- migration retry is available;
- Erabi never continues against a partially trusted schema.

## 17. Integrity Checks

### Lightweight startup check, always active

- database readability;
- migration consistency;
- required tables and indexes;
- artifact directory availability;
- unfinished transaction/job state;
- current-version pointer sanity.

### Deep check

- database integrity;
- referential consistency;
- approved-version immutability;
- current-version pointers;
- artifact existence and hashes;
- audit consistency;
- backup readability when selected.

Deep checks are manual and schedulable. Automatic schedule is off by default.

## 18. Graceful Shutdown

Graceful shutdown is mandatory with a fixed three-second deadline in the MVP.

On SIGTERM, Ctrl+C, service stop, or controlled fatal condition:

1. stop accepting jobs and mutations;
2. expose `SHUTTING_DOWN` health state;
3. signal cancellation tokens;
4. finish active atomic database transactions;
5. persist best-effort checkpoints;
6. mark remaining active jobs Recoverable;
7. flush critical logs and audit summaries;
8. release process and migration locks;
9. exit by the deadline.

The application does not wait for a full page crawl or large download to complete.

## 19. Panic Isolation

Task-level panic is contained at worker boundaries:

- API and unrelated workers continue;
- the job becomes Failed or Recoverable;
- the latest checkpoint remains;
- redacted panic and backtrace receive a trace ID;
- retries are bounded.

Expected failures use typed `Result` values, not panic.

Critical invariant failures involving database consistency, queue trust, migration state, or approved immutability stop mutations and enter Recovery Mode or controlled shutdown.

## 20. Disk-Pressure Protection

Erabi monitors available storage and exposes configurable warning and critical thresholds.

At critical pressure:

- block new artifact-heavy jobs;
- checkpoint active jobs at safe boundaries;
- keep UI and database available;
- offer retention preview, cleanup, and diagnostics;
- never delete automatically unless a cleanup schedule was explicitly enabled beforehand.

## 21. Update Policy

There is no auto-update.

Docker images use pinned version tags. Optional update checks may notify the user, but installation remains manual:

```bash
docker compose pull
docker compose up -d
```

Migrations and integrity checks run on startup. Failed upgrades enter Recovery Mode.

## 22. Backup Defaults

Backup/Restore are available in the MVP. Automatic backup and scheduled deep integrity checks are off by default. These choices are visible in Settings and diagnostics.
