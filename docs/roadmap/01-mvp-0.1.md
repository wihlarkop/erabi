# Erabi Roadmap — MVP 0.1

# 3. Milestone 0.1.0 — Crawler Studio MVP

## Product outcome

A local user can go from **one URL** to a **reusable published crawler**, test and preview it safely, run it with live observability, curate provenance-rich extracted data, and export approved datasets without writing crawler code.

This is the first milestone that should be described publicly as a working Erabi release.

## 3.1 Start / Quick Scrape

### In scope

- input-first Start page;
- single-page Quick Scrape;
- optional advanced crawl settings;
- live progress;
- automatic Draft save;
- automatic Review opening;
- Document vs Records mode suggestion;
- mode switch without recrawl;
- Save as Crawler draft;
- recent actionable activity.

### Not in scope

- blocking onboarding wizard;
- AI-assisted crawler generation;
- arbitrary browser action recording.

### Exit evidence

A new user can run the app, paste a fixture/public URL, see progress, inspect the result, and save it as a Crawler without visiting Settings first.

## 3.2 Crawler Studio design model

### In scope

- Crawler identity;
- optional Collection grouping;
- multiple Seeds;
- Draft and immutable Published Crawler Versions;
- active published version pointer;
- Page Types;
- priority + specificity Page Type matching;
- explicit `AMBIGUOUS_PAGE_TYPE` state;
- `UNMATCHED` preservation/no traversal default;
- Discovery Transitions;
- inspectable visual graph + accessible list equivalent;
- cyclic transitions with budgets;
- URL canonicalization;
- Domain Scope Policy;
- Run Profiles;
- temporary per-run operational overrides;
- Publish Validation Gate;
- Test Evidence.

### Explicit MVP simplification

The graph is **inspectable/visual**, but configuration editing is still panel/form-based. Dragging arbitrary nodes/edges as a visual programming language is deferred.

### Exit evidence

A user can model a multi-page fixture site such as `Category → Listing → Product Detail`, include Listing pagination, test every Page Type/transition, and publish an immutable version.

## 3.3 Test Lab

### In scope

- test URL canonicalization;
- test Page Type matching;
- test extraction;
- test selector coverage;
- test pagination;
- test one transition;
- preview discovered URLs;
- compare draft behavior with active published version where meaningful;
- durable Test Evidence.

### Exit evidence

A crawler draft can be iterated without a production run and the Publish screen can show which Page Types/transitions have current test evidence.

## 3.4 Discovery Preview

### In scope

- bounded sample crawl;
- seed/depth/page/transition limits;
- discovered/canonical URL counts;
- duplicates prevented;
- Page Type distribution;
- ambiguous/unmatched/external/blocked views;
- transition counts;
- robots-policy impact;
- growth warnings;
- graph/tree inspection of discovery paths.

### Exit evidence

A deliberately cyclic fixture site can be previewed without runaway traversal, and the UI explains which transition generated growth.

## 3.5 Production Runs and durable jobs

### In scope

- `QUICK_SCRAPE`, `TEST_RUN`, `DISCOVERY_PREVIEW`, `PRODUCTION_RUN`;
- durable Turso-backed job state;
- leases/heartbeat;
- crash/stale-job recovery;
- queue priorities;
- per-domain/global concurrency controls;
- live SSE progress with replay;
- cooperative Cancel;
- checkpoint Resume;
- Retry Failed Parts;
- Rerun Full Crawl;
- run comparison;
- immutable run configuration snapshots;
- no-change outcome without empty review.

### Exit evidence

A multi-page production fixture can be cancelled during execution, application restarted, and the run safely resumed or restarted with an auditable configuration snapshot.

## 3.6 Safe crawling

### In scope

- robots respect by default;
- explicit audited override path;
- transparent customizable User-Agent;
- per-domain rate limit;
- `Retry-After` handling;
- large-crawl estimate/warning;
- max page/depth/duration/storage budgets;
- domain scope and external-link preservation;
- canonical URL deduplication;
- low-storage safety stop without automatic deletion.

### Exit evidence

Tests prove a discovered cross-domain link cannot silently escape scope and tracking-query variants do not consume duplicate crawl budget.

## 3.7 Extraction Studio

### In scope

- sanitized rendered preview;
- container-first visual selection;
- heuristic field suggestions;
- manual selector editing;
- CSS selectors + fallback evidence;
- live record preview;
- Document and Records mode;
- field types: Text, Rich Text, Number, Boolean, Date/Time, URL, Image URL, Raw HTML;
- raw/normalized value separation;
- selector coverage;
- bidirectional Preview ↔ Field ↔ Record highlighting.

### Exit evidence

A non-technical user can turn a repeated fixture listing into structured records and visually verify the origin of each mapped field.

## 3.8 Datasets and curation

### In scope

- one primary Dataset per Page Type by default;
- multiple Page Types may share a compatible Dataset;
- publish-time shared Dataset compatibility validation;
- explicit/composite unique keys;
- field-level enrichment/conflict candidates;
- source preference ranking only, never silent winner;
- validation ERROR/WARNING;
- ERROR blocks approval and cannot be overridden;
- Approve All Valid skips invalid records;
- rejection with required reason for bulk rejection;
- immutable approved versions;
- semantic normalized-value change detection;
- NEW/UPDATED/MISSING/RESTORED candidate lifecycle;
- complete-snapshot guard before missing detection;
- Close/Reopen Review;
- Dataset relationships by extracted key/reference;
- `UNRESOLVED_REFERENCE` warning.

### Exit evidence

Listing and Detail Page Types can enrich one Products Dataset without silent overwrites, preserving separate provenance for conflicting candidate values.

## 3.9 Provenance

### In scope

Field-level provenance tracks:

- original/canonical source URL;
- Crawler + Version;
- Crawl Run;
- Page Type;
- transition/discovery path where applicable;
- raw artifact reference/hash;
- selector/source element;
- raw value;
- normalized value;
- transformation;
- extraction time.

The Review UI exposes a provenance drawer.

### Exit evidence

For an approved value, a user can trace the value back to exact source/run/artifact/config evidence after later recrawls occur.

## 3.10 Assets

### In scope

- URL + metadata discovery by default;
- Assets tab;
- explicit Download Selected;
- safe image preview;
- safe streaming download;
- MIME/extension mismatch warning;
- checksums;
- local file removal without deleting URL metadata;
- untrusted-file/path hardening.

### Exit evidence

Assets cannot path-traverse outside the asset directory and are never auto-executed/extracted.

## 3.11 Exports

### In scope

- JSON;
- JSONL;
- CSV;
- Markdown;
- SQLite;
- Turso;
- approved-only standard exports;
- optional provenance ZIP bundle;
- manifest + SHA-256 checksums;
- optional downloaded assets in bundle;
- saved destination + Test Connection;
- atomic Create New / Replace database export modes;
- `FILE_REMOVED` history after physical export deletion.

### Deferred from 0.1

- Append;
- Upsert;
- Regenerate Export from old ExportRun;
- custom export filename;
- PostgreSQL/MySQL destination.

## 3.11.1 Internal Turso persistence modes

### In scope

- Local Turso application database as the default mode;
- optional local-first Turso Cloud sync using explicit push/pull semantics;
- sync credentials from environment / `.env`;
- local operation remains fully usable without a cloud account;
- sync state and failures are visible/diagnosable rather than silently ignored.

### Deferred from 0.1

- stateless/direct remote-only application database deployment as a required mode;
- multi-instance writers against one hosted control-plane database.

Those later modes should use the current official Turso remote path available at implementation time rather than adding a legacy libSQL dependency merely for symmetry.

### Exit evidence

Local-only mode works offline, while an explicitly configured sync mode can push and pull against a controlled Turso environment without changing the Erabi domain model.

## 3.12 Backups and recovery

### In scope

- Database Only backup;
- Full Backup;
- `.erabi-backup` format;
- optional password encryption;
- manual Create/Verify/Restore/Delete;
- automatic backup setting default OFF;
- migration backup option;
- startup lightweight integrity check;
- manual deep integrity check;
- optional scheduled deep check default OFF;
- Recovery Mode;
- migration lock;
- single local instance lock;
- `erabi doctor`;
- diagnostic bundle;
- three-second graceful shutdown;
- panic isolation.

### Exit evidence

A deliberately damaged migration/invariant scenario enters Recovery Mode without running crawler mutations, and a valid backup can be verified before restore.

## 3.13 Security MVP

### In scope

- bind `127.0.0.1` by default;
- non-loopback requires shared access token;
- sessionStorage token default, explicit remember option;
- same-origin UI/API;
- explicit CORS allowlist only;
- Origin/Host/Content-Type/body-limit hardening;
- strict security headers/CSP;
- sandboxed crawl preview;
- `.env` for secrets;
- secret redaction;
- structured logs;
- no telemetry default;
- OpenAPI local-only default.

### Exit evidence

A non-loopback startup without token fails closed, and security tests cover protected SSE/download/export/raw-artifact endpoints.

## 3.14 Accessibility and UI baseline

### In scope

- WCAG 2.2 AA target;
- keyboard use;
- screen-reader semantics;
- graph/list equivalent;
- accessible data grid + Card View;
- reduced motion;
- light/dark/system theme;
- English i18n keys;
- optional browser notifications OFF by default;
- metadata global search/command palette.

### Deferred from 0.1

- in-app Notification Center;
- Bahasa Indonesia/Japanese translated catalogs;
- full-text dataset search.

## 3.15 Distribution and verification

### In scope

Docker Compose is the primary MVP distribution:

```text
erabi
crawl4ai
```

The Erabi container serves Rust API/runtime plus built SvelteKit static UI. Crawl4AI uses an official image and remains independently replaceable with an external endpoint.

PR CI uses deterministic Crawl4AI mocks; scheduled smoke tests run real Crawl4AI against local fixture sites.

No auto-update in MVP. Users update version-pinned images manually.

### 0.1 release gate

No 0.1 release until the critical E2E flows in the verification spec pass and public README describes only implemented capabilities.
